# Taste — Command Code
- Requires all dependencies and runtime artifacts (venv, pip/model caches, vector stores, logs) to stay isolated inside the project workspace — no global installs, nothing written outside the repo. Never edit, rewrite, or create files outside the workspace; if something is needed, fetch/install it into the workspace itself. Confidence: 0.9
- Reuse what's already installed on the machine instead of re-downloading dependencies; only download when the dependency is genuinely missing, and then install it into the workspace. Confidence: 0.8
- Wants to execute all git operations himself — commit, push, remote, branch, reset, etc. Never run state-changing git commands on his behalf; only print the exact commands (with the shell variant spelled out, plus verification and fallback steps) for him to run. Same applies to running servers/tests/builds. Confidence: 0.9
- Wants startup/run instructions kept as short as possible — a single combined one-liner per service, with no redundant env vars or setup steps. Confidence: 0.7
- Runs commands in Windows PowerShell 5.1 — run/startup commands must be valid there (`;` / `Set-Location`, not `&&`); give the PowerShell-correct form by default. Confidence: 0.6
- When he asks a question, answer it directly and concisely; don't create code, files, or launchers unless he asks for them ("jawab saja jangan buat code dlu"). For decisions like "can we skip X?", give a short pro/con plus a clear recommendation instead of an essay. Confidence: 0.75
- Wants to be briefed and to approve before anything is acted on: research/explore first, report findings and a recommendation, and wait for his go-ahead before integrating or building. Confidence: 0.65
- Wants derived artifacts (e.g. a redacted/public variant) produced by editing the already-written file rather than regenerating the content from scratch. Confidence: 0.5
- Wants blunt, realistic feasibility assessments ("apakah realistis?") — treat stated requirements (e.g. what a grader demands) as fixed constraints and say plainly what is/isn't achievable instead of proposing to drop them or overclaiming. Confidence: 0.55
- Never claim implementation, validation, novelty, or test results that haven't actually been proven — state only what was really demonstrated. Confidence: 0.75
- Prioritizes simple, obvious UI/UX over feature-dense interfaces — if a UI feels confusing to a normal end user, simplify it (fewer controls/steps, clearer flow) rather than adding more. Confidence: 0.6
- Prefers incremental, justified refactoring over wholesale rewrites: audit first, preserve still-relevant components (engines, rule/evidence layers, existing test suites) and change architecture in stages with regression tests. Confidence: 0.7
- His dev machine is low-spec ("laptop spek kentang": CPU-only, ~12 GB single-channel RAM, no GPU) — model/tooling recommendations must fit that, and he wants the RAM/performance limits stated honestly. Confidence: 0.65
- Does not want to run LLMs locally at all ("gw gamau pakai model lokal") — recommends/plans around hosted API providers (e.g. Google AI Studio/Gemini) even when local small models were offered as fallback; keep the API key in a gitignored `.env`, never in code/README. He also wants the unused local-provider config (e.g. `OLLAMA_*` vars) actively removed from the live `.env` once a hosted provider is chosen, not left lying around. Confidence: 0.65
- Prefers project status/scope reported as a table — one row per component with done / partial / not-done status, a one-line detail, and where the evidence lives — rather than prose lists; detail should be concise but not so terse that it loses meaning. Confidence: 0.65
